# Lightfolio WinUI 3 迁移方案

## 目标

将 Lightfolio 从当前的 Electron + React + TypeScript 桌面应用，逐步迁移为以 WinUI 3 + C# + XAML 为主的 Windows 原生桌面应用。

这次迁移的核心目标不是单纯替换 UI 技术栈，而是同时完成以下三件事：

- 建立更适合大图库的本地桌面架构
- 获得更稳定的 Windows 原生交互与渲染表现
- 为后续几千到几万张媒体资产的浏览、索引和缓存留出空间

## 为什么现在迁移

当前项目的产品边界仍然比较清晰，功能规模尚可控，重写成本还没有高到不可接受。

同时，当前应用的长期瓶颈已经比较明确：

- Electron 对图片密集型界面的基础内存和渲染开销偏高
- 浏览器渲染栈在大图浏览、复杂布局、透明效果和连续切图时更容易出现抖动和额外合成成本
- 当前数据层和 UI 层仍处于可重构阶段，尚未形成难以迁移的复杂业务耦合

结论：现在适合做“保留现有产品理解，重建原生桌面底座”的迁移，而不是继续把 Electron 方案做重后再切换。

## 迁移原则

1. 采用并行迁移，不直接删除现有 Electron 工程。
2. 先建立 WinUI 3 可运行骨架，再迁移数据模型、存储、索引和首屏流程。
3. 优先迁移数据与交互骨架，不在第一阶段追求完整视觉还原。
4. 优先解决大图库基础能力：本地库、缩略图、分页、窗口化、异步加载。
5. 保持现有产品语义不变：本地索引、非破坏性移除、回收站删除、时间轴浏览、详情编辑。

## 目标架构

建议新增独立的 .NET 解决方案，并与现有 Node monorepo 并存。

建议目录结构：

- winui/Lightfolio.sln
- winui/Lightfolio.WinUI: WinUI 3 桌面壳、页面、控件、ViewModel
- winui/Lightfolio.Core: 导入、索引、存储、缩略图、EXIF 读取
- winui/Lightfolio.Infrastructure: SQLite、文件系统、缩略图缓存、系统集成
- winui/Lightfolio.Contracts: 共享领域模型、DTO、查询参数、操作结果

第一批重构不一次性拆满四个项目，可以先从两个项目开始：

- Lightfolio.WinUI
- Lightfolio.Contracts

当导入、缩略图、SQLite 和 EXIF 逻辑开始落地时，再补 Lightfolio.Core 和 Lightfolio.Infrastructure。

## 从现有代码映射到 WinUI 3

现有 TypeScript 层的职责映射建议如下：

- app/src/main: 迁移为 .NET 文件系统服务、导入服务、缩略图服务、系统对话框服务
- app/src/preload: 不再需要，改为 ViewModel 直接调用应用服务
- app/src/renderer/src/components: 迁移为 WinUI 页面、UserControl、自定义控件
- core/src/indexer: 迁移为 C# 导入与时间轴构建服务
- core/src/metadata: 迁移为 C# EXIF 服务
- core/src/storage: 迁移为 SQLite 或本地数据库服务
- shared/src/types.ts: 优先迁移为 C# 领域模型和契约层

## 技术决策

### UI 技术

- UI 框架：WinUI 3
- 语言：C#
- 模式：MVVM
- 状态组织：ViewModel + 命令 + 可观察集合

### 本地数据层

- 第一阶段：保留轻量本地快照能力，先跑通应用启动和状态恢复
- 第二阶段：升级为 SQLite
- 原因：几千到几万张资产下，需要稳定索引、分页、筛选和增量更新能力

### 缩略图与预览策略

- 缩略图与原图分离
- 列表和时间轴永远使用缩略图，不直接展示原始大图
- 单图页采用分阶段加载：缩略预览 -> 中等分辨率 -> 原图
- 缓存分层：内存 LRU + 磁盘缩略图缓存

### 导入策略

- 使用稳定资产键，至少包含 path + size + mtime
- 支持重复导入去重
- 支持增量导入，只重新处理变更文件
- 启动时不全量解码图片，只恢复索引与首屏所需缩略图

### 包装方式

- 初期优先采用可本地调试的 WinUI 3 项目结构
- 是否采用 Packaged MSIX 作为默认交付方式，放到第二阶段确定
- 原因：先降低迁移复杂度，优先拿到可运行原生版本

## 分阶段计划

## Phase 0: 建立原生骨架

目标：在仓库内新增 WinUI 3 解决方案，具备可启动主窗口和基础页面结构。

交付物：

- WinUI 3 工程创建完成
- 主窗口、应用入口、主题资源可运行
- Shell 页面具备三栏骨架或占位布局
- 基础领域模型完成第一批迁移

## Phase 1: 迁移领域模型与本地库读取

目标：让 WinUI 3 版本能加载本地库快照并展示基础资产列表。

交付物：

- AssetRecord、TimelineGroup、ImportSummary、LibrarySnapshot 等模型迁移完成
- 本地快照读取服务完成
- 首屏加载流程完成
- 选中资源、当前视图、折叠状态等 UI 状态可恢复

## Phase 2: 迁移浏览骨架

目标：建立可用的时间轴、单图查看、底部胶片带和右侧详情面板。

交付物：

- Shell 布局完成
- 时间轴列表和单图查看切换完成
- 详情面板基础字段展示完成
- 文件夹筛选、搜索、收藏/精选过滤完成第一版

## Phase 3: 迁移导入与索引链路

目标：摆脱对旧 Electron 主进程的依赖，在 WinUI 3 下完成导入、扫描和索引。

交付物：

- 文件选择与目录选择流程完成
- 媒体扫描完成
- 去重、索引构建、月分组完成
- 快照写回与状态持久化完成

## Phase 4: 缩略图缓存与大图库性能优化

目标：让 WinUI 3 版本具备几千到上万张素材下仍可用的滚动与浏览能力。

交付物：

- 磁盘缩略图缓存
- 内存 LRU 缓存
- 列表窗口化和增量加载
- 单图查看分阶段解码
- 首屏延迟加载和后台预取

## Phase 5: 视觉与交互收口

目标：恢复并提升当前产品气质，使其更接近 Windows 原生照片应用体验。

交付物：

- 三栏布局与间距体系稳定
- 动画、面板切换、主图切换手感统一
- 键盘、鼠标滚轮、双击、全屏等交互补齐
- 删除确认、Toast、错误态、空态和加载态补齐

## 第一批直接落地范围

这次开始重构时，只做最小可行切入，不一次性迁完整应用。

本轮实现范围：

- 新增 WinUI 3 解决方案与主应用工程
- 建立 App、MainWindow、Shell 页面
- 建立基础 Models 和 ViewModels
- 建立本地快照读取服务
- 首屏展示库摘要与基础资产列表
- 保留 Electron 工程不删除

本轮不做：

- 完整导入链路迁移
- SQLite 落地
- EXIF 迁移
- 缩略图磁盘缓存重建
- 主图缩放、拖拽、连续预加载
- 完整视觉还原

## 风险与应对

### 风险 1：WinUI 3 工具链未完整安装

当前环境已确认有 .NET SDK，但未安装 WinUI workload 和模板。

应对：

- 先安装官方模板包
- 若本机缺少 Visual Studio 相关组件，则先完成工程骨架和代码迁移，再由本机补齐开发依赖后编译

### 风险 2：过早追求 UI 还原导致迁移拖慢

应对：

- 第一阶段只做结构和数据流
- 视觉细节推迟到浏览链路稳定后处理

### 风险 3：数据层仍沿用轻量 JSON 快照导致性能迟早受限

应对：

- 先用快照跑通流程
- 第二阶段尽快切 SQLite

### 风险 4：TypeScript 逻辑无法直接复用

应对：

- 不纠结代码复用率
- 直接复用现有产品模型、字段定义、数据语义和交互理解

## 验收标准

第一批重构完成时，应达到以下标准：

1. WinUI 3 工程已进入仓库并能恢复依赖。
2. 应用可启动到主窗口。
3. 可从本地库快照加载资产数据。
4. 可在原生 UI 中看到至少一版基础图库列表。
5. 现有 Electron 版本仍保留，便于对照迁移。

## 接下来立即执行的动作

1. 创建 WinUI 3 工程与解决方案。
2. 建立 Shell 页面和基础 ViewModel。
3. 迁移共享模型到 C# 契约层。
4. 接入现有快照文件读取。
5. 在 WinUI 3 中显示库摘要与资产列表。

以上步骤完成后，再继续推进导入、时间轴、详情面板和缩略图缓存。
